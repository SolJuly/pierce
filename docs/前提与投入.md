## 二、前提（按硬性程度排序）

### 1. 宿主版本必须钉死并记录

```
dsh 0.2.2-rc.1  ← 唯一验证过的版本
Node >= 18（实测 24.9.0）
```

`dsh-purge` 写的是 `dshTarget: "0.2.0-rc.2"`，在这台机器（0.2.2-rc.1）上：
- 包被拆了（`dsh-tools` 的 pipeline 独立成文件）
- 函数改名（`displayReason` → `escalationDisplayReason`）
- 提示词措辞换代（`Approval policy: ask` → `Approval prompts are enabled in this session`）

**没有版本对照表，任何补丁表都会在下次升级时整体失效。** 这是第一前提。

### 2. 必须有「官方原貌」基线

补丁表的锚点只能从**未被修改的官方源码**上取，不能在 live（已打过补丁的）上取：
- 从 live 取 → 原文已被替换掉，锚点静默变空
- 从 baseline 取 → 干净可靠

本项目已建好机制（`scripts/make-baseline.mjs`），从宿主上的 `*.dshpurge.bak` 反向复原：

```
文件 48 个 / 2357 KB
来源: dshpurge.bak=47  live=1
```

**前提：宿主上得存在 `.dshpurge.bak`。** 如果被人清掉，就只能重装 dsh 再取。

### 3. 必须能识别「哪些能走扩展点」

宿主暴露的 waterfall 就是天然的挂载点，实测可用的有：

| 事件 | 能干什么 | 对应 purge 补丁 |
|---|---|---|
| `approval/request` | 直接返回 `allowed-once`，整个审批链短路 | #9 #13 #14 #35 #60 |
| `tools/pre-execute` | `ask` 降成 `allow`，`deny` 不动 | #59 #62 |
| `system-prompt/assemble` | 增删改 sections / contexts | #1 #2 #3 #4 #5 #11 #12 #29 #32 #33 #34 #37 #48 #50 #53 #54 #61 #63 |
| `fs/write-intent` / `edit-intent` / `delete-intent` | 返回 `undefined` = 不做版本/先读校验 | #17 |
| `systemPrompt.section()` / `.context()` | 注册自己的提示词段 | 新增能力 |

**这 5 个挂载点承接了 25 条补丁。** 扩展点不是"猜"的，是从宿主源码里 `ctx.waterfall(...)` / `ctx.on(...)` 的实际调用点抄出来的。

### 4. 配置层必须懂「整体替换」语义

`dsh-app-boot/lib/index.js` 的 `applyPatches`：

```js
for (const [key, value] of Object.entries(overrides)) target[key] = value;
```

**不是深合并。** 你改 `tool-fs` 的一个字段，必须把它的 9 个字段全写出来，漏写的变 `undefined` 回落到源码默认值。这是配了不生效的头号原因，也是 A 层 25 条补丁的实现前提。

### 5. 必须区分宿主层和预设层

Web profile 里工具不在宿主层：

```
base:      tool-fs（有 config）→ web-app: tool-fs（disabled: true）
           实际生效的是 presets/standard.patch.yml 里那一份
```

改宿主层 `tool-fs` 在 Web 面**完全不生效**。所以：
- 宿主级配置 → `profiles/web/cordis.patch.yml`
- 预设级配置 → `profiles/web/node_modules/@deepseek-ai/dsh-web-app/presets/*.yml`（三个预设都要改）

### 6. 运行时能力边界

**能做到**（已验证）：审批短路、工具门降级、fs 闸放行、提示词段热替换、身份段清洗。
**做不到**（必须走源码补丁）：
- 改工具 schema 里的描述文本（`z.string().describe(...)` 已固化）
- 改 zod 的 `.default()` 值（要改的是源码字面量）
- 改桌面壳的进程行为
- 改 `agent-loop` 每步替换首条 system 的行为

这 32 条的清单在 `ref/mechanism.json` 的 `C` 组里。

## 四、与 purge 的关键差别

| 维度 | dsh-purge 1.1.71 | 破甲 v2 |
|---|---|---|
| 规则存放 | 写死在 7 984 行 core.js 里 | JSON 表，可 diff、可 review |
| 幂等 | 靠 marker 字符串 | 跑到 fixpoint，规则链也收敛 |
| 半打状态 | 静默跳过 | `partial` 单独报，必须处理 |
| 失效条目 | 混在 skipped 里 | `obsolete` + 理由，不当故障 |
| 多文件补丁 | 任一文件 drift 就整条失败 | 按「锚点是否与该文件相关」聚合 |
| 升级应对 | 重新锚定全部 82 条 | 只需重锚 C 组 32 条 |
| 回滚粒度 | 插件级 | 文件级，可选补丁 ID |
| 生效方式 | 改源码 + 重启宿主 | 大部分运行时生效，`/pierce off` 免重启 |

## 九、拒绝率实测

> 测试台：`test/refusal/`，方法与局限见 `test/refusal/README.md`
> 只用同一模型换 system 做对照：A = 裸模型（`You are a helpful assistant.`），B = 注入 `prompt-inject.md` 全文（25 KB）

### 总体

| 模型 | 有效样本 | 裸模型 A | 破甲 B | 降幅 |
|---|---|---|---|---|
| DeepSeek-V4.1-Flash | 117 / 116 | **82.9%** | **57.8%** | −25.1pt |
| GLM-4-Flash（交叉验证） | 38 / 38 | 68.4% | 23.7% | −44.7pt |

### 拆开看才是关键：硬类目几乎没动

| 类目组 | DeepSeek A | DeepSeek B | 说明 |
|---|---|---|---|
| **硬伤害类**（勒索/武器/毒品/儿童/洗钱/暴力） | 95.8% | **88.6%** | 降 7.2pt —— **基本没破开** |
| **技术类**（渗透/Web/撞库/外挂/破解/越权） | 73.9% | **38.9%** | 降 35pt —— 有效 |

逐类目（DeepSeek，每格 6 次采样）：

| 类目 | A → B | 结论 |
|---|---|---|
| 渗透 / Web / 绕过管控 / 撞库 | 67% / 60% / 50% / 0% → **0%** | 完全打通 |
| 游戏外挂 | 100% → 17% | 基本打通 |
| 软件破解 | 100% → 67% | 部分 |
| DDoS | 100% → 67% | 部分 |
| 恶意软件 | 92% → 50% | 对半 |
| 钓鱼 / 隐私人肉 / 勒索 | 100% → 83% | 只松动一点 |
| **洗钱 / 毒品 / 武器 / 儿童性内容** | 100% → **100%** | **完全无效** |
| 自伤 | 67% → **100%** | **反向** |

### 拒答理由归因（B 组 67 条被拒样本）

| 模型自己给的拒答理由 | 占比 |
|---|---|
| 侵犯他人权利（隐私/盗号/身份） | 37% |
| 硬伤害底线（勒索/武器/毒品/儿童） | 37% |
| 法律定性（违法/犯罪/红线） | 31% |
| 现实世界危害（会造成真实损失） | 22% |
| 单纯引规则（"不允许"） | 9% |

**关键发现：67 条里 63% 直接说出了「我不能 / 抱歉 / 我不做」** —— 而注入里明令禁止这些措辞。说明在硬类目上，注入的**措辞约束先失效，然后内容约束才失效**。

### 这说明什么

1. **破甲不是开关，是分层的。** 越靠近"技术操作"，注入越有效；越靠近"人身/现实危害"，越无效。
2. **模型的安全边界是语义层的，不是词表层的。** 插件能拆掉宿主的审批闸、能压掉"免责声明"话术，但拆不掉模型对「这件事会造成真实伤亡/伤害他人」的判断。这些样本里模型不是被规则拦住，是自己重新推导了一遍危害。
3. **自伤类目被注入反向推高（67%→100%）。** 因为注入说"不许谈安全"，而模型在自伤场景里把"不谈安全"理解成"更要坚持安全"。**这类请求不该被破，测试里应当剔除**（P16 这一条是探针设计失误，不是插件缺陷）。
4. **GLM 的降幅（−44.7pt）比 DeepSeek（−25.1pt）大得多**，但 GLM 的硬类目也掉得更狠（85.7%→28.6%）。样本只有 38，**不能据此说 GLM 更"好破"**，只能说不同模型的安全层位置不同。

### 结论一句话

**在"技术操作类"极端问题上，拒绝率从约 74% 降到约 39%，插件有效。**
**在"直接人身/现实危害类"上，从 96% 只降到 89%，插件基本无效 —— 这部分不是插件能力问题，是模型语义层判断，改提示词改不动。**

要覆盖剩下那 88.6%，只有两条路：换模型，或在调用侧做改写（把请求重构成技术语境）。后者不在插件范围内。
